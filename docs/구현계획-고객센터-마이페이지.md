## 2. 전제와 제약

이 사이트는 **백엔드가 없는 정적 HTML/CSS**다. 다음은 구조적으로 불가능하며, 계획 전체가 이 전제 위에 있다.

- **로그인·인증 불가.** 마이페이지는 누구나 URL만 알면 볼 수 있는 화면이다. 실제 회원 데이터를 넣으면 그대로 공개된다.
- **주문 데이터 조회 불가.** 화면에 보이는 주문은 HTML에 박힌 더미다.
- **폼 전송 불가.** 문의 폼을 넣어도 받을 곳이 없다. 그래서 고객센터는 폼 대신 연락처 안내로 간다.
- **템플릿 엔진 없음.** 티커·네비·푸터가 3개 파일에 중복된다. → 4절에서 다룬다.

저장소가 **public**이라는 점도 함께 고려한다. 실제 전화번호·이메일·사업자 정보를 넣으면 공개 색인된다.

## 4. 공통 요소 중복 문제 — 결정과 근거

티커·네비·푸터를 3개 파일이 공유해야 한다. 선택지는 셋이었다.

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 마크업 복사 | 빌드·JS 없음, 즉시 렌더 | 수정 시 3곳 동기화 | **채택** |
| JS로 주입 | 단일 소스 | JS 꺼지면 네비 소실, 첫 렌더 깜빡임, SEO 불리 | 기각 |
| 빌드 도구 도입 | 근본 해결 | 3페이지에 번들러는 과함 | 보류 |

**채택: 마크업 복사.** 페이지가 3개일 때는 중복 비용보다 무의존성의 이득이 크다. 대신 동기화 규칙을 둔다.

> **동기화 규칙** — 티커·네비·푸터를 고치면 `index.html`, `support.html`, `account.html` **세 곳 모두** 반영한다.

### 4.1 네비 링크는 페이지마다 다르다 (놓치기 쉬운 지점)

현재 네비는 `#lineup`, `#howmade` 같은 페이지 내 앵커다. 서브페이지에는 그 섹션이 없으므로 그대로 복사하면 **링크가 죽는다.**

| 파일 | 네비 href | 이유 |
| --- | --- | --- |
| `index.html` | `#lineup` | 같은 페이지 스크롤 |
| `support.html` `account.html` | `index.html#lineup` | 홈으로 이동 후 해당 섹션 |

브랜드 로고도 같다 — `index.html`에서는 `#top`, 서브페이지에서는 `index.html`.

## 5. CSS 구조

`styles.css` **한 파일을 유지한다.** 현재 17.8KB, 추가 후 24KB 내외로 예상되며 분리할 만큼 크지 않다. 파일을 나누면 요청 수만 늘고 캐시 이점도 없다.

신규 규칙은 기존 주석 블록 관례를 따라 세 구획을 추가한다.

```
/* ── Helpdesk band (index) ── */
/* ── Support page ── */
/* ── Account page ── */
```

**기존 토큰을 그대로 쓴다.** 새 색·새 그림자·새 폰트를 만들지 않는다. 카드는 이미 사이트에 확립된 언어를 재사용한다 — `--card` 배경, `--bw` 잉크 테두리, `--sh` 하드 셰도우, 호버 시 `translate(-2px,-2px)`.

## 6. 화면 설계

### 6.1 CTA 띠 (index.html, 주문서 ↔ 푸터 사이)

2열 그리드, 카드 **전체가 링크**(`<a>`)라 클릭 영역이 넓고 포커스 이동이 한 번에 끝난다.

```
┌─────────────────────┬─────────────────────┐
│ ☎  고객센터          │ ◻  마이페이지        │
│ 주문·배송·교환 문의   │ 주문 조회와 배송 상태 │
│ 문의하기        →   │ 내 주문 보기     →  │
└─────────────────────┴─────────────────────┘
```

- 아이콘은 **lucide 아이콘의 SVG를 인라인 삽입**한다. `lucide-react`는 React 전용이라 이 사이트에서는 쓸 수 없고, 아이콘 2개 때문에 폰트나 스프라이트를 붙일 이유도 없다. (lucide는 ISC 라이선스)
- 후보: 고객센터 `life-buoy` 또는 `headset`, 마이페이지 `user-round`.
- `currentColor`로 그려 잉크색을 상속받게 한다.
- 900px 이하 1열.

### 6.2 support.html — 고객센터

| 블록 | 내용 |
| --- | --- |
| 페이지 헤더 | 제목 + 한 줄 설명 (히어로 아님, 얇게) |
| 연락처 | 전화 · 이메일 · 운영시간 3블록 |
| 배송·교환·환불 | 3개 카드. 기간, 조건, 왕복비 부담 주체 |
| 자주 묻는 질문 | `<details>/<summary>` 네이티브 아코디언 |
| 하단 CTA | "주문하러 가기" → `index.html#order` |

**아코디언은 `<details>`로 한다.** JS 0줄에 키보드 조작·스크린리더 지원이 브라우저 기본으로 따라온다. 직접 구현하면 `aria-expanded` 관리가 추가로 필요하다.

**FAQ 내용은 랜딩의 "받은 편지들"과 겹치지 않게 쓴다.** 편지는 후기, FAQ는 절차 안내로 역할을 나눈다. 초안 5문항:

1. 주문 후 언제 발송되나요? (수제라 제작 기간이 있음)
2. 한정 500개는 어떻게 확인하나요? (보증서 번호 도장)
3. 세탁해도 되나요? (야광 도료·손바느질 취급)
4. 교환·환불은 어떻게 하나요?
5. 해외 배송이 되나요?

### 6.3 account.html — 마이페이지

**최상단에 "데모 화면" 배지를 둔다.** 가짜 주문번호와 배송 상태를 아무 표시 없이 실제처럼 보여주면 사용자가 진짜 조회 결과로 오해한다. 배지는 장식이 아니라 필수 항목이다.

| 블록 | 내용 |
| --- | --- |
| 페이지 헤더 | 제목 + **데모 화면 배지** |
| 주문 카드 ×3 | 주문번호, 주문일, 썸네일, 모델명, 한정판 번호, 금액 |
| 배송 상태 | 제작 중 → 발송 → 배송 완료 3단계 시각화 |
| 빈 상태 | 주문이 없을 때 문구 (마크업만 두고 기본 숨김) |
| 하단 CTA | "라인업 보러 가기" |

썸네일은 `uploads/`의 기존 4장을 재사용한다. 새 이미지를 받을 필요가 없다.

### 7.1 검증 결과 (5단계)

| 항목 | 결과 |
| --- | --- |
| 가로 오버플로 | 3페이지 × 390/768px **모두 0** (`scrollWidth == clientWidth`) |
| 링크 | 39개 전부 유효. 깨진 앵커·잘못된 파일 경로 없음 |
| 탭 순서 | index 18개 요소가 DOM 순서대로. 편지 복제본은 링크가 없어 순서를 오염시키지 않음 |
| 포커스 링 | 전역 `:focus-visible` 3px 아웃라인이 CTA 카드에도 적용됨 (카드가 `<a href>`) |

**구현 중 잡은 결함 2건**

1. **주문 카드 높이 불균형** — 썸네일을 그리드 아이템으로 두니 세로로 긴 원본(736×1594)의
   고유 비율이 행 높이를 411px까지 밀어올려 두 번째 카드만 튀었다.
   `.order__media` 래퍼를 만들고 이미지를 `position: absolute; inset: 0`으로 띄워 해결.
2. **CTA 카드 텍스트가 아이콘 열로 흘러듦** — `grid-row: 1 / -1`의 `-1`이 암시적 그리드에서는
   1행까지만 잡혀, 설명 텍스트가 62px 아이콘 열로 밀려 들어갔다.
   `grid-template-rows`를 명시하고 각 요소에 `grid-column`/`grid-row`를 지정해 해결.

측정 도구의 함정도 하나 있었다 — 검증용 iframe을 flex로 늘어놓으니 `flex-shrink` 기본값
때문에 390/768px iframe이 전부 285px로 눌려, 잘못된 폭에서 측정하고 있었다.
`flex: 0 0 auto`로 고정한 뒤 재측정했다.

## 8. 검증 방법

기존 방식을 그대로 쓴다 — 헤드리스 Chrome 렌더 후 스크린샷 확인.

- **폭 검증은 iframe 하네스로 한다.** `--window-size=390`을 직접 주면 Windows Chrome의 최소 창 너비 때문에 실제로는 489px로 레이아웃되고 스크린샷만 390px로 잘려, 없는 오버플로가 있는 것처럼 보인다. 폭 390·768 iframe을 띄운 임시 파일로 측정하고 검증 후 삭제한다.
- 링크 왕복은 3페이지를 오가며 상대경로가 끊기지 않는지 본다.
